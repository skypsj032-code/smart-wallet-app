# Recurring Transaction Suggestion Design

작성일: 2026-05-07

## 1. 요약

이번 기능의 목적은 기존의 `고정 지출` 개념을 `정기 거래`로 확장하고, 날짜가 되었을 때 자동 생성하지 않고 홈에서 `추천 후 생성` 흐름으로 처리하는 것이다.

핵심 방향:

- `지출`과 `수입` 모두 지원한다.
- `매주`, `매달` 반복을 지원한다.
- 날짜가 되어도 거래를 자동 생성하지 않는다.
- 홈에는 `가장 중요한 추천 1개`만 알림 카드처럼 노출한다.
- 사용자는 `생성`하거나 `이번엔 닫기`만 선택하면 된다.
- 로컬 알림은 이번 범위에서 제외한다.

## 2. 문제 정의

현재 앱에는 `고정 지출` 기능이 있지만 다음 한계가 있다.

- 지출 전용 개념에 가깝다.
- 주기 표현이 제한적이다.
- 홈에서 “오늘 처리할 정기 거래”를 자연스럽게 알려주지 못한다.
- 자동으로 거래를 만들지 않더라도, 생성 시점을 사용자에게 묻는 흐름이 없다.

사용자가 원하는 것은 다음과 같다.

- `매달 5일 급여`
- `매달 10일 통신비`
- `매주 월요일 회비`

같은 항목을 규칙으로 등록해두고, 날짜가 되면 앱이 알아서 “생성할까요?”라고 묻는 구조다.

## 3. 목표

- 기존 `고정 지출`을 `정기 거래` 개념으로 일반화한다.
- 홈에서 정기 거래 추천을 `알림 카드 1개`로 보여준다.
- 날짜가 되었을 때 자동 생성하지 않고 사용자 승인 후 생성한다.
- `이번엔 닫기`를 누르면 현재 추천만 숨긴다.
- 홈의 달력/통계와 추천 알림의 성격을 분리한다.

## 4. 비목표

이번 단계에서 하지 않는 것:

- 자동 생성
- 로컬 푸시/시스템 알림
- 여러 추천을 한 번에 리스트로 노출
- 복잡한 반복 규칙 (`격주`, `매월 마지막 영업일`, `N번째 월요일` 등)
- 추천 우선순위 사용자 커스터마이징
- 여러 추천을 처리하는 전용 대시보드

## 5. 접근안 비교

### 접근안 A. 자동 생성

- 날짜가 되면 앱이 거래를 바로 생성한다.

장점:

- 가장 편하다.

단점:

- 사용자가 마지막 확인 없이 거래가 생기는 걸 원하지 않는다.
- 금액이나 상황이 변했을 때 잘못된 기록이 생길 수 있다.

### 접근안 B. 추천 후 생성

- 날짜가 되면 홈에 추천 카드만 띄운다.
- 사용자가 승인할 때만 거래를 생성한다.

장점:

- 사용자가 최종 통제권을 가진다.
- 자동화와 수동 검토 사이 균형이 좋다.
- 홈을 과하게 복잡하게 만들지 않고도 안내할 수 있다.

단점:

- 앱을 열어야 확인할 수 있다.

### 접근안 C. 추천 리스트

- 처리 대상이 여러 개면 홈에 리스트로 나열한다.

장점:

- 한 번에 많은 항목을 처리할 수 있다.

단점:

- 홈이 복잡해진다.
- 사용자는 홈을 간결하게 유지하길 원한다.

## 6. 선택

이번 기능은 `접근안 B. 추천 후 생성`으로 간다.

추가로 홈 노출 방식은 `가장 중요한 추천 1개만` 사용한다.

이유:

- 홈의 밀도를 억제할 수 있다.
- 정기 거래의 존재는 알려주되, 강하게 기능 허브처럼 보이지 않는다.
- 자동 생성보다 안전하고, 추천 리스트보다 단순하다.

## 7. 최종 설계

### 7.1 개념 변경

현재 `고정 지출`은 `정기 거래`로 확장된다.

정기 거래는 다음을 포함한다.

- 거래 타입: `income | expense`
- 반복 단위: `weekly | monthly`
- 규칙:
  - weekly: 요일
  - monthly: 날짜
- 금액
- 이름
- 계좌
- 카테고리
- 활성 여부

즉, 모델은 더 이상 지출 전용이 아니다.

### 7.2 정기 거래 관리 화면

기존 `고정 지출` 화면은 사실상 `정기 거래 관리` 화면이 된다.

등록/수정 시 필요한 입력:

- 수입/지출
- 이름
- 금액
- 계좌
- 카테고리
- 반복 단위
- 요일 또는 날짜

1차 반복 규칙:

- `매주 월~일 중 1개`
- `매달 1~31일 중 1개`

### 7.3 추천 발생 규칙

홈 추천 카드는 `오늘 처리 대상인 정기 거래`가 있을 때만 등장한다.

기본 규칙:

- `monthly`
  - 오늘 날짜가 등록한 날짜와 같으면 후보가 된다.
- `weekly`
  - 오늘 요일이 등록한 요일과 같으면 후보가 된다.

추가 조건:

- 이미 이번 주기에서 생성 처리된 항목은 다시 띄우지 않는다.
- `이번엔 닫기`를 눌러 dismiss된 항목도 이번 주기에는 다시 띄우지 않는다.

즉, 추천은 “오늘 해당되지만 아직 이번 회차를 처리하지 않은 정기 거래”만 대상으로 한다.

### 7.4 홈 노출 방식

홈에서는 정기 거래 추천을 `알림 카드`로 다룬다.

중요:

- 달력/통계 카드와 같은 블록 안에 넣지 않는다.
- 별도의 독립 카드로 둔다.
- 일반 기능 카드가 아니라 상태성 알림처럼 보여야 한다.

노출 수:

- 홈에는 `가장 중요한 1개만` 노출한다.

### 7.5 추천 우선순위

후보가 여러 개일 때 1차 우선순위는 단순하게 유지한다.

추천 우선순위:

1. 오늘이 정확히 일치하는 항목
2. 최근 처리 시점이 더 오래된 항목
3. 그래도 같으면 생성일이 더 오래된 항목

이 규칙이면 홈에는 항상 1개만 안정적으로 뜬다.

### 7.6 알림 카드 UI

카드 구성:

- 제목
  - 예: `오늘 처리할 정기 거래가 있어요`
- 본문
  - 예: `통신비 55,000원`
  - 예: `급여 3,200,000원`
- 보조 정보
  - `매달 10일`
  - `매주 월요일`
- 액션
  - `생성`
  - `이번엔 닫기`

### 7.7 액션 동작

`생성`

- 해당 정기 거래를 일반 거래로 생성한다.
- 생성 후 이번 주기에서는 다시 추천하지 않는다.
- 홈 카드도 즉시 사라진다.

`이번엔 닫기`

- 이번 추천만 숨긴다.
- 영구 삭제가 아니다.
- 다음 주기/다음 달에는 다시 후보가 될 수 있다.

### 7.8 데이터 처리

정기 거래 추천을 위해 각 규칙에는 “이번 주기에서 처리했는지”를 판단할 정보가 필요하다.

필요한 추적 정보 예:

- 마지막 생성 주기 키
- 마지막 dismiss 주기 키

주기 키 예:

- monthly: `2026-05`
- weekly: `2026-W19`

이 값으로 “이번 회차에 이미 생성했는지 / 닫았는지”를 계산한다.

### 7.9 거래 생성 방식

추천에서 `생성`을 누르면 일반 거래를 만든다.

생성될 거래는 정기 거래 규칙의 템플릿을 따른다.

포함되는 값:

- type
- amount
- occurredAt = 오늘
- accountId
- categoryId
- memo 또는 name

즉, 추천 카드에서 사실상 템플릿 기반 빠른 생성이 일어난다.

## 8. 화면 관계 정리

홈:

- 달력 미리보기
- 통계 미리보기
- 정기 거래 추천 알림 카드(있을 때만)

도구:

- 정기 거래 관리 화면 진입

정기 거래 관리 화면:

- 규칙 등록
- 수정
- 비활성화/삭제

## 9. 테스트 전략

### 단위 테스트

- monthly 규칙이 오늘 날짜와 맞으면 후보가 되는지
- weekly 규칙이 오늘 요일과 맞으면 후보가 되는지
- 이번 주기에서 이미 생성한 항목은 후보에서 제외되는지
- 이번 주기에서 dismiss한 항목은 후보에서 제외되는지
- 후보가 여러 개면 우선순위 1개만 선택되는지

### 위젯 테스트

- 홈에서 추천 카드가 조건부로 보이는지
- `생성` 누르면 카드가 사라지고 거래가 생기는지
- `이번엔 닫기` 누르면 카드가 사라지는지
- 달력/통계와 별도 카드로 렌더링되는지

### 회귀 테스트

- 기존 고정 지출 생성 흐름이 정기 거래 구조로 바뀐 뒤에도 깨지지 않는지
- 홈이 추천 카드 때문에 과하게 길어지지 않는지

## 10. 구현 메모

- 기존 `recurring_expenses` 모델/서비스를 기반으로 확장하는 것이 가장 자연스럽다.
- 이름은 점진적으로 `recurring transactions` 의미로 옮기되, 마이그레이션 비용은 최소화한다.
- 홈 추천은 “목록”이 아니라 “대표 1건 카드”여야 한다.
- 로컬 알림은 후속 단계로 분리한다.
