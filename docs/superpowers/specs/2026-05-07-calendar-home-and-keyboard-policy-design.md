# 달력·홈 미리보기·전역 키보드 입력 정책 설계

작성일: 2026-05-07

## 1. 요약

이번 변경의 목적은 세 가지다.

- 달력 화면을 `일별 / 월별 / 연별` 스위치 기준으로 다시 정리한다.
- 홈의 달력/통계 미리보기를 접힘 구조에서 `항상 펼쳐진 축약형`으로 바꾼다.
- 키보드가 입력 UI를 가리는 문제를 달력 한 화면이 아니라 앱 전체 입력 정책으로 해결한다.

핵심 원칙:

- 홈은 요약만 보여주고, 눌렀을 때 상세 화면으로 들어간다.
- 달력은 보기 전환과 기록 입력이 한 화면 안에서 자연스럽게 이어진다.
- 입력 UI는 화면마다 임시로 고치는 것이 아니라 공통 규칙으로 맞춘다.

## 2. 목표

- `주간` 중심 구조를 제거하고 `일별 / 월별 / 연별` 중심으로 달력을 재구성한다.
- 달력 안에서 날짜별 수입/지출을 바로 기록할 수 있게 한다.
- 달력 입력에서 수입/지출, 금액, 카테고리, 계좌, 메모를 모두 다룬다.
- 홈의 달력/통계 미리보기는 접히지 않고 항상 보이게 한다.
- 홈에서 `달력`, `통계` 같은 군집 제목과 불필요한 설명 문구를 제거한다.
- 터치 키보드가 입력 필드를 가리는 문제를 앱 전체에서 일관되게 줄인다.

## 3. 비목표

- 통계의 분석 철학 자체를 다시 설계하지는 않는다.
- 달력 안에서 완전한 새 거래 편집 화면을 대체하지는 않는다.
- 모든 입력 화면을 바텀시트로 바꾸지는 않는다.
- 안드로이드 전용 대응만 넣고 다른 플랫폼을 무시하지는 않는다.

## 4. 접근안 비교

### 접근안 A. 정석 재구성형

- 달력 보기 구조, 홈 미리보기 구조, 키보드 대응 정책을 같이 정리한다.
- 홈은 요약, 달력은 기록, 전역은 입력 안전성이라는 책임 분리를 맞춘다.

장점:

- 구조가 가장 일관된다.
- 이후 달력과 입력 기능 확장 시 덜 꼬인다.
- 사용자가 느끼는 불편이 한 번에 줄어든다.

단점:

- 이번 작업 범위가 가장 크다.

### 접근안 B. 달력 우선형

- 달력 화면과 달력 입력만 먼저 고친다.
- 홈 미리보기와 전역 키보드 정책은 다음 단계로 미룬다.

장점:

- 빠르게 체감 개선이 나온다.

단점:

- 홈은 여전히 어정쩡하고, 키보드 문제도 다른 화면에 남는다.

### 접근안 C. 홈 우선형

- 홈의 미리보기 구조만 먼저 바꾼다.
- 달력 입력과 키보드 정책은 뒤로 미룬다.

장점:

- 메인 화면 인상은 빨리 좋아진다.

단점:

- 사용자가 실제로 불편한 입력 문제는 그대로 남는다.

## 5. 선택

이번 구현은 `접근안 A. 정석 재구성형`으로 간다.

이유:

- 사용자는 홈 구조와 달력 구조, 입력 불편을 하나의 흐름으로 느끼고 있다.
- 이 셋을 따로 고치면 같은 문제를 다른 형태로 다시 보게 된다.
- 지금 시점에서는 구조를 한 번 정리하는 편이 총 비용이 낮다.

## 6. 최종 설계

### 6.1 홈 구조

홈의 달력/통계 영역은 더 이상 접히지 않는다.

- 달력 미리보기는 항상 보인다.
- 통계 미리보기는 항상 보인다.
- 둘 다 축약형 미리보기 상태를 유지한다.
- 눌렀을 때만 각 상세 화면으로 이동한다.

삭제할 것:

- `달력`, `통계`를 묶는 군집 제목
- 두 기능의 연관성을 설명하는 문장
- 접힘/펼침 상태 관리

레이아웃 방향:

- 모바일 비율 기준 `세로 배치`
- 위에 달력 축약형
- 아래에 통계 축약형

### 6.2 홈 달력 미리보기

홈 달력 미리보기는 작은 월간 달력을 그대로 유지하되, 항상 펼쳐진 형태로 보인다.

포함:

- 작은 월간 캘린더
- 이번 달 또는 오늘 기준 건수/수입/지출 요약
- 미리보기 전체를 누르면 달력 화면으로 이동

제외:

- 필터
- 보기 전환
- 입력 폼

즉, 홈 달력은 `보여주기 전용 미리보기`다.

### 6.3 홈 통계 미리보기

홈 통계 미리보기는 항상 보이는 작은 요약 영역으로 둔다.

포함:

- 상위 지출 카테고리 3개
- 핵심 숫자 일부
- 미리보기 전체를 누르면 통계 화면으로 이동

제외:

- 필터 토글
- 차트 세부 조작
- 긴 설명 문구

즉, 홈 통계는 `한눈 요약 + 상세 진입` 역할만 한다.

### 6.4 달력 보기 구조

달력 화면의 보기 전환은 `일별 / 월별 / 연별`로 바꾼다.

- `주간`은 제거한다.
- `일별`은 하루 단위 상세 보기다.
- `월별`은 지금의 메인 달력 역할을 이어받는다.
- `연별`은 월 요약 그리드로 유지한다.

#### 일별

- 선택한 날짜 하나를 중심으로 본다.
- 상단에는 날짜 정보와 간단한 요약이 나온다.
- 그 아래에 거래 목록과 빠른 입력 카드가 나온다.

#### 월별

- 월간 캘린더가 메인이다.
- 날짜를 누르면 해당 날짜가 선택되고, 화면 아래에 일별 상세가 갱신된다.
- 빠른 입력 카드도 선택 날짜 기준으로 같이 갱신된다.

#### 연별

- 월 단위 요약 카드 그리드를 유지한다.
- 월을 누르면 해당 월의 월별 화면으로 들어간다.

### 6.5 달력 안 빠른 입력

달력에서 직접 입력하는 방식은 `선택한 날짜 아래 인라인 빠른 입력 카드`다.

포함 필드:

- 수입/지출 타입 전환
- 금액
- 카테고리
- 계좌
- 메모
- 저장 액션

동작 원칙:

- 날짜를 먼저 선택해야 열린다.
- 저장되면 해당 날짜 집계와 목록이 즉시 갱신된다.
- 더 많은 수정이 필요하면 기존 상세 입력 화면으로 이동할 수 있다.

### 6.6 달력 입력과 기존 빠른 입력 화면의 관계

달력 인라인 입력은 `경량 입력`이다.

- 새 거래를 바로 남기는 데 최적화한다.
- 기존 `QuickEntryScreen`은 여전히 상세 편집/수정용으로 유지한다.

즉:

- 달력 인라인 입력 = 빠른 작성
- 기존 빠른 입력 화면 = 전체 편집

### 6.7 전역 키보드 정책

이 문제는 달력만의 문제가 아니라 앱 전체 입력 UX 정책으로 다룬다.

정책은 세 층으로 나눈다.

#### A. 전체 화면 입력 폼

- `AppScaffold` 기반 화면은 기본적으로 키보드 inset을 반영한다.
- 본문이 입력 중심이면 스크롤 가능한 컨테이너 안에 둔다.
- 하단 여백은 `MediaQuery.viewInsets.bottom`을 기준으로 늘어난다.

적용 후보:

- 빠른 입력
- 검색
- 계좌/예산/반복지출 입력
- OCR 검토 입력

#### B. 다이얼로그 입력

- 입력 필드가 있는 다이얼로그는 `SingleChildScrollView`와 bottom inset 대응을 강제한다.
- 키보드가 떠도 버튼과 입력칸이 밀려 올라오게 한다.

적용 후보:

- PIN 설정
- 카테고리 생성/수정
- 예산/반복지출 소형 입력 다이얼로그

#### C. 바텀시트 입력

- 입력 바텀시트는 `isScrollControlled: true`를 기본 정책으로 한다.
- 내부는 `SafeArea + AnimatedPadding(viewInsets.bottom)` 기준으로 정리한다.

적용 후보:

- 선택형 입력
- 짧은 생성 폼

## 8. 테스트 방향

### 달력

- `일별 / 월별 / 연별` 전환 테스트
- 월별에서 날짜 선택 시 일별 상세가 바뀌는지 확인
- 달력 안 빠른 입력 저장 후 날짜 집계가 갱신되는지 확인
- 연별에서 월 탭 시 월별로 이동하는지 확인

### 홈

- 달력/통계 미리보기가 항상 보이는지 확인
- 접힘 상태 관련 테스트 제거 또는 갱신
- 카드 전체 탭 시 각 상세 화면으로 이동하는지 확인

### 전역 입력 정책

- 키보드 inset 반영 단위 테스트/위젯 테스트
- 입력 다이얼로그에서 하단 버튼이 가려지지 않는지 확인
- 바텀시트 입력이 키보드와 함께 위로 올라오는지 확인

### 수동 확인

- 안드로이드 터치 키보드
- 윈도우 터치 키보드
- 작은 세로 프레임에서 입력창이 가려지지 않는지 확인

## 9. 구현 순서 제안

1. `AppScaffold`와 공통 입력 정책 정리
2. 홈 미리보기에서 접힘 구조 제거
3. 달력 보기 모드 `일별 / 월별 / 연별` 재구성
4. 달력 인라인 빠른 입력 추가
5. 관련 테스트 갱신

## 10. 열린 결정

이번 설계에서 이미 고정한 결정:

- 홈 미리보기는 접히지 않는다.
- 홈 미리보기는 세로 배치다.
- 달력 입력은 인라인 카드 방식이다.
- 키보드 문제는 전역 정책으로 푼다.

남은 구현 세부사항:

- 달력 인라인 입력이 기존 quick entry form state를 얼마나 재사용할지
- 홈 통계 미리보기에서 보여줄 숫자 밀도
- 각 입력 화면별 `AppScaffold` 적용 수준
