# Solo Development Workflow

작성일: 2026-05-18

## 목적

이 문서는 Smart Wallet을 1인 개발 기준으로 운영할 때, `왜 이렇게 결정했는지`와 `다음에 무엇을 해야 하는지`를 남기기 위한 기본 규칙을 정리한다.

핵심 목표는 세 가지다.

1. 중요한 기능 결정이 나중에 다시 봐도 이해되게 만든다.
2. 기능 단위로 다음 행동이 바로 이어지게 만든다.
3. 팀 수준의 무거운 프로세스가 아니라, 혼자서도 계속 지킬 수 있는 가벼운 운영 방식을 유지한다.

## 운영 원칙

- 작업의 기본 단위는 `기능`이다.
- 모든 기능은 `spec / plan / result` 3문서를 남긴다.
- 문서 구조는 고정하고, 문서 길이는 기능 크기에 따라 줄인다.
- 문서의 역할은 회고가 아니라 `판단 근거`와 `다음 행동`을 연결하는 것이다.
- 애매하면 기능 크기를 한 단계 크게 잡는다.

## 기능 크기 분류

### Small

- 파일 1~3개 수준의 변경
- UI 한 군데 수정, 로직 한 군데 수정, 문구/상태/간단한 플로우 추가
- 반나절 안쪽 작업
- 되돌리기 쉬움

### Medium

- 파일 여러 개 수정
- UI, 상태, 데이터 흐름 중 2개 이상이 함께 바뀜
- 하루~이틀 이상 걸릴 수 있음
- 테스트나 검증 포인트가 분명히 생김

### Large

- 기능 묶음 하나를 새로 여는 수준의 작업
- 데이터 모델, 여러 화면, 상태 관리, 마이그레이션, 정책 변화까지 걸침
- 며칠 이상 걸릴 수 있음
- 설계 실수 비용이 큼

## 기능 크기 판단 규칙

기능 크기는 코드 줄 수로 판단하지 않는다. 아래 3가지를 본다.

1. 몇 개 층을 건드리는가
2. 되돌리기 어려운가
3. 다음 작업에 구조적 영향을 남기는가

파일 하나만 고치더라도 DB 스키마나 제품 규칙이 바뀌면 `small`이 아니다.

## 문서 폴더 구조

- `docs/features/specs/`
- `docs/features/plans/`
- `docs/features/results/`

기능 문서는 항상 이 3개 폴더에 나눠 저장한다.

## 파일명 규칙

- `YYYY-MM-DD-<feature-slug>-spec.md`
- `YYYY-MM-DD-<feature-slug>-plan.md`
- `YYYY-MM-DD-<feature-slug>-result.md`

예시:

- `2026-05-18-auto-ledger-dashboard-spec.md`
- `2026-05-18-auto-ledger-dashboard-plan.md`
- `2026-05-18-auto-ledger-dashboard-result.md`

규칙:

- 날짜는 기능 시작일 기준
- `feature-slug`는 짧고 일관되게 유지
- 같은 기능의 spec, plan, result는 같은 slug를 사용

## Small 기능 템플릿

### Spec

- 왜 하는지
- 사용자에게 뭐가 달라지는지
- 이번에 안 하는 것

권장 길이: `3줄`

### Plan

- 바꿀 파일
- 할 일 2~4개
- 확인 방법 1줄

권장 길이: `4~6줄`

### Result

- 실제로 바뀐 것
- 계획과 달라진 점
- 다음 할 일 또는 없음

권장 길이: `3줄`

## Medium 기능 템플릿

### Spec

- 왜 하는지
- 해결하려는 문제
- 사용자에게 뭐가 달라지는지
- 범위
- 비범위
- 리스크 또는 애매한 결정 1~2개

권장 길이: `6~10줄`

### Plan

- 바꿀 파일 또는 레이어
- 구현 단계 3~7개
- 테스트 또는 확인 방법
- 막힐 수 있는 지점

권장 길이: `8~15줄`

### Result

- 실제로 바뀐 것
- 계획과 달라진 점
- 검증 결과
- 남은 일

권장 길이: `6~10줄`

## Large 기능 템플릿

### Spec

- 왜 하는지
- 문제 정의
- 목표
- 비목표
- 사용자 흐름
- 범위
- 비범위
- 핵심 설계 원칙
- 리스크
- 오픈 질문

### Plan

- 바뀌는 구조
- 데이터, 상태, UI 영향
- 단계별 구현 순서
- 마이그레이션 여부
- 테스트 전략
- 검증 체크포인트
- 롤백 또는 안전장치

### Result

- 실제로 바뀐 것
- 설계 대비 달라진 점
- 검증 결과
- 남은 리스크
- 후속 작업
- 다음 기능으로 넘길 수 있는 상태인지

## 기능 시작, 진행, 종료 규칙

### 시작

- 기능을 잡으면 먼저 `spec`을 만든다.
- 이어서 `plan`을 만든다.
- `spec / plan`이 없으면 코드를 먼저 건드리지 않는다.

### 진행

- 구현 중 판단이 바뀌면 `plan`을 먼저 수정한다.
- 이유가 바뀌면 `spec`도 함께 수정한다.
- 문서는 회고용이 아니라, 현재 기준의 최신 판단을 반영해야 한다.

### 종료

- 검증이 끝나면 `result`를 만든다.
- `실제로 바뀐 것`, `계획과 달라진 점`, `다음 할 일`을 기록한다.
- 기능 종료는 코드 작성이 아니라 `result`까지 정리된 시점으로 본다.

## 1인 개발 기준 Git 운영 규칙

### 기본 원칙

- 문서 3종이 기능 기록의 중심이고, Git은 그 기록을 안전하게 남기는 수단이다.
- 작은 작업마다 팀처럼 무거운 PR 절차를 강제하지 않는다.
- 다만 큰 결정, 구조 변경, 며칠 이상 걸리는 작업은 브랜치와 PR로 기록을 강화한다.

### 브랜치 규칙

- `small`: 현재 작업 흐름을 깨지 않는 선에서 같은 브랜치에서 처리 가능
- `medium`: 기본적으로 기능 브랜치 사용 권장
- `large`: 반드시 기능 브랜치 사용

기능 브랜치 이름 규칙:

- `codex/<feature-slug>`
- 버그 수정은 필요하면 `codex/fix-<feature-slug>`

기본 브랜치는 현재 원격 기본 브랜치를 따른다. 현재 저장소 기준 기본 브랜치는 `master`다.

### 커밋 규칙

- 기능 단위로 커밋 의도를 명확하게 남긴다.
- 최소한 기능 종료 시점에는 `result`가 반영된 커밋이 있어야 한다.
- 커밋 메시지는 짧고 일관되게 유지한다.

권장 접두어:

- `feat:`
- `fix:`
- `docs:`
- `refactor:`
- `chore:`

권장 방식:

- 기능 시작 시 `spec / plan` 추가 커밋 가능
- 구현 완료 후 `result`와 실제 코드 변경을 묶어 마무리 커밋

### PR 규칙

- `small`: PR 선택 사항
- `medium`: 기록 가치가 있으면 PR 권장
- `large`: PR 권장

Draft PR을 쓰는 경우:

- 범위가 아직 열려 있음
- 며칠 이상 이어질 가능성이 큼
- 방향 리뷰가 먼저 필요함

Ready PR로 전환하는 조건:

- `spec / plan / result`가 모두 최신 상태임
- 검증 결과가 정리돼 있음
- 남은 리스크나 후속 작업이 명확히 적혀 있음

### PR 없이 끝내는 경우

PR을 열지 않더라도 아래는 지킨다.

- 기능 문서 3종은 남긴다.
- 최종 커밋에는 `result`까지 반영한다.
- 다음 기능으로 넘어가기 전, 남은 작업이 무엇인지 문서에서 바로 보이게 한다.

## 권장 기본 흐름

1. 기능 시작
2. `spec` 작성
3. `plan` 작성
4. 필요하면 기능 브랜치 생성
5. 구현 진행
6. 판단 변경 시 `spec / plan` 갱신
7. 검증 완료
8. `result` 작성
9. 커밋
10. 필요하면 PR 생성 또는 기존 브랜치에 로컬 정리

## 이 방식이 1인 개발에 맞는 이유

- 중요한 결정은 남기되, 작은 기능 문서는 극단적으로 짧게 유지할 수 있다.
- 미래의 내가 다시 봤을 때 `왜 이렇게 했는지`를 바로 복구할 수 있다.
- 다음 기능으로 넘어갈 때 `무엇이 끝났고 무엇이 남았는지`가 문서만 봐도 이어진다.
- 팀용 프로세스를 흉내 내는 것이 아니라, 혼자서도 계속 유지 가능한 최소 규칙만 남긴다.

## 예외

다음은 기능 문서 3종 대신 일반 커밋만으로 끝낼 수 있다.

- 단순 오타 수정
- 로그 제거
- 주석 정리
- 사용성 영향이 거의 없는 문구 수정

단, 이런 변경이 기능 흐름이나 제품 판단에 영향을 주면 다시 기능 단위 문서로 올린다.
